# 범용(비 K-CURE) 데이터 변환 — 구현과 시험 결과

- 시험일: 2026-10-19
- 목적: K-CURE 항목정의서(1,255항목)에 없는 일반 병원 데이터도 같은 변환기로 바꿀 수 있는지 확인합니다. 대상은 입원·외래·검사·처방 데이터입니다.
- 샘플: Google Drive「GPT/로컬 LLM 활용 테스트용 더미 데이터셋(Dummy Data) 생성 프롬프트」로 로컬 LLM(Ollama + qwen2.5 7B)이 만든 가상 데이터. **실제 환자 정보는 없습니다.**

## 1. 무엇을 만들었나

| 구성 | 내용 |
|---|---|
| 범용 표준 사전 `spec/generic_spec.json` | 52항목. 이 중 47항목이 KR CDI V3에 연결됩니다. 별칭 413개, 약어 패턴 38개, 문맥 규칙 2개. K-CURE 항목과 같은 구조라서 기존 엔진(매핑·FHIR·KR CDI·DCAT·OMOP·가명처리)을 그대로 씁니다. 생성 스크립트는 `tools/build_generic.py` |
| '범용' 모드 | ① 화면에서 **범용(비 K-CURE)**을 고르거나 컬럼 파일을 불러오면 됩니다. 범용 사전으로 잡히는 컬럼이 K-CURE보다 많으면 자동으로 범용으로 판정합니다. K-CURE 암종 모드의 매핑 결과는 바뀌지 않습니다 |
| 컬럼명 대조 | ① 별칭 사전 → ② 약어 패턴(CamelCase를 단어로 나눔: `PatientName` → `patient_name`) → ③ 문맥 규칙('단위'는 바로 앞 컬럼이 투여량이면 투여량 단위, 결과값이면 결과 단위) |
| 세로형(long) 검사 데이터 | 같은 행의 검사코드·검사명·참고치·판정을 결과값 Observation 의 `code`·`referenceRange`·`interpretation` 으로 붙입니다 |
| 코드+명칭 합치기 | 약품코드+약품명, 진단코드+진단명을 리소스 하나(CodeableConcept의 code·text)로 합칩니다 |
| **직접식별자 차단(보안 수정)** | 가명처리 ON이면 성명·연락처·주소·의료인 이름·의료인 ID를 FHIR·KR CDI·로그에서 모두 뺍니다. 가명처리 OFF면 `Patient.name`·`telecom`·`address`로 바르게 표현합니다 |
| 샘플 생성기 `tools/gen_dummy_llm.py` | Drive 프롬프트 원문(A)과 같은 형식을 변형한 프롬프트(B·C)로 로컬 LLM에서 생성합니다. B·C의 **컬럼명은 LLM이 자유롭게** 짓습니다 |
| 시험 페이지 `tests/generic_test.html` | 샘플별로 매핑 → 6개 표준 메타데이터 → FHIR·KR CDI → 가명처리 코드 → 경과기록 PII를 한 번에 시험합니다 |

## 2. 샘플 데이터

| 세트 | 프롬프트 | 컬럼(LLM 생성) | 행 | 생성 시간 |
|---|---|---|---|---|
| A | Drive 원문 그대로 | PAT_ID, AGE, GENDER, DIAG_CODE, ADMIT_DATE + 경과기록 3건 | 50 | 168초 |
| B | 변형: 외래 혈액검사, 영문 약어 | ID, PatientName, TestTime, TestCode, TestName, Result, Unit, RefRange, Interpretation | 30 | 178초 |
| C | 변형: 고혈압·당뇨 처방, 한글 | 등록번호, 성명, 생년월일, 성별, 연락처, 처방일, 진단코드, 약품코드, 약품명, 1회투여량, 단위, 투여경로, 1일투여횟수, 처방일수, 처방의 이름 + 진료기록 2건 | 30 | 322초 |

**7B 모델 더미의 품질 한계:**
- A의 진단코드가 KCD 형식이 아닙니다(`1101`).
- B의 검사명이 중국어로 나왔습니다(`血糖`).
- C의 '처방의 이름' 칸에 의사 이름이 아니라 메모가 들어갔습니다.
- 경과기록에는 이름 같은 PII가 거의 없습니다.

변환기 시험용으로는 쓸 수 있지만, 값의 의미를 검증하려면 큰 모델(ChatGPT 등)로 만든 더미나 규칙 기반 생성기를 함께 쓰는 것이 좋습니다.

## 3. 결과

### 3.1 컬럼 자동 매핑 (정답 = 컬럼 의미에 맞는 범용 사전 항목, 사람이 지정)

| 세트 | 블라인드(사전 v0.1.0, 샘플을 보기 전 작성) | 보완 후(v0.1.1) | 블라인드에서 틀린 컬럼 → 보완 |
|---|---|---|---|
| A | 5/5 | 5/5 | — |
| B | 7/9 | **9/9** | `ID`(단독 ID 미인식), `Interpretation`(약어 패턴 없음) → 단독 ID·interp 패턴 추가 |
| C | 14/15 | **15/15** | `단위`(검사결과 단위로 오인) → 앞 컬럼 문맥 규칙 |
| 합계 | **26/29 (89.7%)** | **29/29** | 보완은 모두 일반 규칙(특정 값 하드코딩 없음) |

### 3.2 변환 결과 (보완 후, 가명처리 ON)

| 세트 | FHIR 리소스 | 구조 오류 | KR CDI 값 | KR CDI 항목 | 메타 파일 | DCAT 필수 누락 | 직접식별자 원문 노출 |
|---|---|---|---|---|---|---|---|
| A | 200 (Patient·Encounter·Condition·Observation 각 50) | 0 | 200 | 4 | 24 | 0 | 0 |
| B | 60 (Patient 30·Observation 30) | 0 | 210 | 7 | 24 | 0 | 0 |
| C | 90 (Patient·Condition·MedicationRequest 각 30) | 0 | 360 | 14 | 24 | 0 | 0 |

- B의 검사 Observation 30건은 모두 검사코드(code)·참고구간(low/high)·판정(H/L/N)이 붙었습니다.
- C의 처방은 약품코드+약품명이 1건으로 합쳐졌습니다. 보완 전에는 60건으로 나뉘었습니다.
- 남은 경고는 데이터에 없는 KR CDI 필수 항목 안내뿐입니다(예: 생년월일·진단일자 없음).

| 세트 | 결과 컬럼 | 원본 해시 | 가명키 = 변환기 방식 | 재현성 |

### 3.4 시험 중 발견한 보안 문제와 조치

범용 데이터를 처음 넣었을 때 **가명처리를 켰는데도 성명·연락처 원문이 FHIR 확장(extension)과 KR CDI 결과에 남았습니다.** K-CURE 항목정의서에는 이름·연락처 항목이 없어서 드러나지 않던 경로입니다.

- 조치: 변환 파이프라인에서 직접식별자 경로(`Patient.name`·`telecom`·`address`, `Practitioner.name`·`identifier` 등)와 범용 사전의 `directId` 항목을 가명처리 ON일 때 제외합니다. 로그에는 '제외했다'는 사실만 남깁니다.
- 회귀 방지: 자동 테스트 2건(원문 미포함·제외 기록)과 범용 시험의 '직접식별자 원문 노출' 지표를 추가했습니다.

## 4. 재현 방법

```bash
python tools/gen_dummy_llm.py A B C        # Ollama 실행 중이어야 함 (약 11분)
python tools/build.py
python tools/devserver.py                  # 다른 창에서
```
그 다음 `http://localhost:8765/tests/generic_test.html`을 열고, 끝나면 `python tools/verify_generated.py tests/_out/generic_pkg_B.zip samples/generic/B_정형.csv`를 실행합니다.

## 5. 남은 과제

- 범용 사전 범위 넓히기: 영상·병리·간호 기록, 응급실, 수술 상세(마취·출혈량), 다중 진단(주/부상병)
- 컬럼명만으로 모호한 경우(`VALUE`, `CODE`, `DATE` 단독)는 샘플값 패턴과 LLM 범주 판정(S5)으로 보완
- 큰 모델로 만든 더미·실제 병원 헤더(가명)로 정확도 재측정
