# 로컬 LLM 실모델 PoC 결과 (S5 1차)

- 시험일: 2026-10-19
- 환경: Windows 11, Intel Core Ultra 7 258V(8코어), RAM 32GB, 내장 GPU Arc 140V
  - Ollama는 이 GPU를 쓰지 않아 **CPU 추론**으로 시험했습니다.
- 모델: Ollama 0.40.5 + `qwen2.5:7b-instruct`(7.6B, Q4_K_M, 4.7GB)
- 경로: 실제 앱과 같은 코드(`KC.deid.plan` → `KC.llm.suggest`, **20개 단위** 비동기 요청)를 썼습니다. 전송만 계측용으로 감쌌습니다.
- 데이터: 합성 병원 추출 컬럼 46개 × 10행(`tests/llm_poc.js`). **실제 환자 정보는 없습니다.**
  - 정답은 컬럼별 허용 기법 목록입니다. 예: 날짜는 `DATE_SHIFT` 또는 `DATE_TO_INTERVAL`.
- 재현: `python tools/devserver.py` 실행 → `http://localhost:8765/tests/llm_poc.html?auto=1&samples=0` 열기 → 결과가 `tests/_out/`에 저장됩니다.
  - 이번 결과 원본은 `docs/poc/*.json`에 있습니다.

## 1. 결과 요약

규칙 엔진만 쓰면 46개 중 **36개**가 정답입니다. 규칙 신뢰도가 '높음'인 6개를 뺀 40개를 LLM에 보냈습니다.

| 프롬프트 | 방식 | 보낸 40개 중 LLM 정답 | 전체 46개 (규칙+LLM) | 안전 병합* | 소요(초) |
|---|---|---|---|---|---|
| v1 | 기법을 직접 판정 | 14 | 21 | — | 185 |
| v2 | 규칙 추천을 보여 주고 검토 | 30 | 36 | — | 195 |
| v3 | 의미 범주 판정 → 기법은 코드가 결정 | 34 | 41 | — | 170 |
| **v3.1 (최종)** | v3 + 약어 힌트 + 누락 컬럼 재요청 | **37** | 43 | **44** | **174** |
| v3.1 + 샘플값 전송 | 위와 같음, 샘플 고유값 3개 포함 | **38** | 44 | **46** | 302 |

\* 안전 병합은 LLM 제안이 규칙보다 보호 수준을 낮출 때(예: 정규식 치환 → 유지) 그 제안을 버리고 규칙을 유지하는 방식입니다. 앱의 '안전한 제안 일괄 적용' 버튼과 같은 규칙입니다.

**결론:** 7B 모델은 컬럼 **의미 분류**는 쓸 만합니다. 반면 가명처리 **기법을 직접 정하는 데는 쓰면 안 됩니다**. 최종 구조는 다음과 같습니다.
- LLM은 범주만 판정하고, 범주 → 기법은 정책표로 정합니다.
- 보호 수준을 낮추는 제안은 자동 적용하지 않습니다.
- 그 결과 규칙 엔진보다 정답이 8~10개 늘었습니다(36 → 44~46). 모든 제안은 '후보' 상태로만 들어가며 담당자 승인이 필요합니다.

## 2. 단계별로 발견한 문제와 조치

| 단계 | 관찰 | 조치 |
|---|---|---|
| v1 | 병기·검사값·Y/N·코드·키·체중 같은 임상 변수 20여 개를 "개인 식별 정보"로 보고 삭제·마스킹(과잉 판정). 후보에 없는 항목ID도 선택 | 임상 변수는 기본 '유지'로 명시. 후보 밖 항목ID는 받지 않도록 검증 강화 |
| v2 | 규칙 추천을 보여 주자 근거에는 "환자 이름(직접식별자)"라고 쓰고도 기법은 규칙의 KEEP을 그대로 따름(앵커링) | 규칙 추천을 프롬프트에서 빼고 판정 과제를 바꿈 |
| v3 | **의미 범주 12종**(NAME·RRN·CONTACT·INSURANCE_NO·PATIENT_ID·BIRTH_DATE·EVENT_DATE·AGE·POSTCODE·INSTITUTION·FREE_TEXT·CLINICAL)만 판정하게 하자 크게 개선. 다만 나이를 CLINICAL로, 일부 자유문을 CLINICAL로 분류했고 2개 컬럼은 응답에서 누락 | 약어·나이·자유문 힌트 추가, 누락 컬럼만 모아 1회 재요청, '보호 수준 낮춤' 판정 추가 |
| v3.1 | 남은 오류: `HP_NO`(휴대폰)를 환자번호로, `ATTEND_DR`(주치의)를 진료과로, 자유문 1~2개를 임상 변수로 분류 | 자유문 오류는 안전 병합이 막아 줌. 약어 해석 오류는 샘플값을 보내면 해결(ATTEND_DR 정답) |

## 3. 성능 (CPU 추론)

- 20개 묶음 1회당 **68~122초**입니다(프롬프트 약 1,900~3,000자, 응답 JSON 19~20행).
- 누락 재요청은 3~6개 묶음이라 24~47초 걸렸습니다.
- 46개 컬럼 전체는 샘플 미전송 **2분 54초**, 샘플 전송 **5분 2초**입니다.
- 모든 요청에서 JSON 형식이 정상이었습니다. 실패한 묶음은 0회이고, 형식 오류 재시도도 없었습니다.
- 수천 컬럼 규모라면 CPU 기준 시간 단위가 걸립니다. 운영 PC에 GPU가 있거나 Ollama가 Intel GPU(Vulkan)를 지원하는지는 병원 인터뷰(S6)에서 확인해야 합니다.

## 4. 브라우저 연결 조건 (중요)

| 여는 방법 | 브라우저가 보내는 출처 | Ollama 기본 설정 |
|---|---|---|
| HTML 파일 더블클릭(`file://`) | `null` | **거부(403)** |
| `http://127.0.0.1:포트` 또는 `http://localhost:포트` | 해당 주소 | 허용 |

- 그래서 LLM 연동본은 `dist/LLM연동_실행.bat`(또는 `python tools/serve_llm.py`)로 **127.0.0.1에 띄워서** 씁니다.
  - Python 내장 웹서버를 127.0.0.1에만 열고, dist 폴더를 읽기 전용으로 제공합니다.
- `OLLAMA_ORIGINS`에 `null`을 넣어도 동작은 합니다. 하지만 그러면 다른 웹페이지(샌드박스 iframe 등)도 이 PC의 LLM을 호출할 수 있게 되므로 **권장하지 않습니다**.

## 5. 남은 과제

- 정답셋을 실제 병원 컬럼 목록(가명 처리된 헤더만)으로 바꿔 다시 측정(S6 인터뷰 때 확보)
- 14B 모델(`qwen2.5:14b-instruct` 등)·EXAONE과 비교. RAM 32GB에서 14B Q4는 CPU로 가능하지만 약 2배 느릴 것으로 예상
- 표준항목 후보 생성 개선. 별칭 사전에 없는 약어 컬럼은 후보가 없어 항목ID 매핑에는 기여하지 못함. 현재 LLM의 효과는 가명처리 범주 판정에 한정됨
